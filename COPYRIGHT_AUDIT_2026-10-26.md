## Подтверждённые недочёты: исправить перед дальнейшим распространением

### 1. В дистрибутивы не попадают тексты лицензий и уведомления Rust-зависимостей — P1

Генератор [tools/package.py:70](E:/Projects/Cds/tools/package.py:70) получает только название, версию, SPDX-выражение и репозиторий. В [tools/package.py:96](E:/Projects/Cds/tools/package.py:96) выводятся лишь первые три поля. Тексты лицензий, copyright и дополнительные NOTICE не собираются; даже сохранённый URL репозитория в таблицу не попадает.

Во всех четырёх опубликованных архивах вне Portable Git присутствуют только собственный `LICENSE`, таблица `THIRD_PARTY_NOTICES.md` и три файла в `licenses/`: Inter, JetBrains Mono, SBCL. В таблицах релиза 322 пакета; текущий lockfile содержит 349 внешних пакетов. Таблица не заменяет требуемые лицензионные материалы.

Конкретные примеры: MIT-ветка `serde`/`regex` требует сохранения соответствующих уведомлений; ISC `libloading` — copyright и permission notice; Apache-only `winit`/`glutin` — выполнения условий раздела 4, включая копию лицензии и применимые уведомления. Для ICU-пакетов нужно учитывать Unicode-3.0, а для выражений с `AND` — все обязательные части. [Apache License 2.0, раздел 4](https://www.apache.org/licenses/LICENSE-2.0).

Исправление: сформировать набор лицензий для фактически поставляемых компонентов, выбрать допустимую ветку каждого `OR`, сохранить copyright/NOTICE и разместить материалы в каждом дистрибутиве. Не ограничиваться копированием одного общего текста MIT. У ряда upstream-crate лицензионные файлы вообще отсутствуют в опубликованном пакете: для них нужно брать документы из точной upstream-ревизии. Само отсутствие такого файла в crate не означает отсутствия лицензии.

Исправление: приложить BSD-уведомления Zstandard, проверить дополнительные уведомления точного поставляемого бинарника и собирать лицензии всех нативных библиотек автоматически. В проверенных DMG других отдельных dylib в `Frameworks` не найдено.

## Дополнительные риски и незакрытые вопросы

### 7. GNU Bash: условия оригинальной графики расходятся с метаданными каталога — высокий приоритет

Наш `gnubash.svg` совпадает с Simple Icons. В метаданных Simple Icons указана MIT. Однако в первоисточнике, включая конкретную ревизию `61eff022f2dad3c7468f5deb4f06652d15f2c143`, на которую ссылается каталог, README обозначает графику как Free Art License и copyright Free Software Foundation 2016; `assets/LICENSE` содержит **FAL 1.3**. Корневой `LICENSE` того же репозитория — MIT с другим copyright. При использовании графики из `assets/` нельзя автоматически игнорировать более конкретные условия каталога.

В Light не приложены ни MIT-уведомление этого оригинала, ни сведения FAL/FSF/авторов графики; общая CC0 эту неопределённость не снимает. FAL предусматривает сведения об авторах, доступ к оригиналам и лицензионные условия для копий/изменений. [Первичный репозиторий Bash logo](https://github.com/odb/official-bash-logo), [FAL 1.3](https://artlibre.org/licence/lal/en/).

До сохранения этого знака нужно определить применимые условия для конкретной версии и производной обложки и выполнить их. Практичная альтернатива — собственное типографическое обозначение shell. Из этого пункта не следует автоматическая обязанность переводить всю IDE под FAL.

### 8. Portable Git: доступ к полным соответствующим исходникам не подтверждён — высокий приоритет

Опубликованный Windows ZIP содержит Portable Git, включая дополнительные Unix-инструменты, а не один `git.exe`. Найдены 88 путей с лицензионными/авторскими материалами внутри `git/`. Это положительно, но не подтверждает выполнение всех обязательств GPL/LGPL-компонентов.

[tools/installers.py:63](E:/Projects/Cds/tools/installers.py:63) добавляет только ссылку на upstream-релиз Git for Windows. Такая же ссылка есть в опубликованном notices. Перечень опубликованных материалов Light не содержит комплекта соответствующих исходников Portable Git. В указанном upstream-релизе перечислены главным образом бинарные пакеты; автоматический архив исходников репозитория Git не содержит соответствующих исходников всех поставляемых Bash/MSYS и других компонентов.

Сама ссылка на upstream не доказывает достаточность схемы распространения. Нужно обеспечить применимый способ предоставления соответствующих исходников, включая нужные версии компонентов и сборочные материалы, либо проверить надлежащее предложение исходников и возможность его передачи. GPLv2/GPLv3 различаются в деталях способов предоставления. [Разъяснения GNU о распространении бинарников и исходников](https://www.gnu.org/licenses/gpl-faq.html#SourceAndBinaryOnDifferentSites).

Это незакрытая обязанность, а не заключение о том, что GPL запрещает включать Git в Light. Запуск самостоятельного Git отдельным процессом и включение его в общий установщик сами по себе не требуют перелицензировать весь собственный код Light под GPL.

### 9. `option-ext` под MPL-2.0: требуется проверить фактически поставляемый код

`option-ext 0.2.0` присутствует через `dirs-sys` в normal/build-графах всех четырёх платформ; notices только перечисляет MPL-2.0 и не объясняет получение исходников. Применение методов этой библиотеки найдено в Linux-специфичном `dirs-sys/src/xdg_user_dirs.rs`. При этом сам Light вызывает `dirs::config_dir()`, а LTO может удалять неиспользуемые функции.

Поэтому **наличие зависимости в Cargo.lock не выдаётся за доказательство распространения её кода на каждой платформе**. Если MPL-код остаётся в поставляемом исполняемом файле, требуется сообщить получателям способ получения соответствующих MPL-исходников. Можно включить точные исходники библиотеки либо установить отсутствие её кода в бинарнике. Это не требует раскрывать весь независимый код IDE. [Mozilla MPL FAQ, вопросы 8 и 11](https://www.mozilla.org/en-US/MPL/2.0/FAQ/).

### 10. Логотипы C++ и Python: отдельно учитывать товарные знаки

Для C++ [первоисточник](https://github.com/isocpp/logos) отсылает к [условиям Standard C++ Foundation](https://isocpp.org/home/terms-of-use): общее разрешение относится к неизменённому знаку в связи с языком и без впечатления одобрения продукта. В Light применяется одноцветная версия из Simple Icons с дополнительным оформлением. Право на такую модификацию этим общим разрешением уверенно не подтверждается. Возможное отдельное согласие в проекте не найдено; это вопрос для уточнения, а не доказанное нарушение товарного знака.

Для Python нельзя объявлять любую перекраску нарушением: [PSF policy](https://www.python.org/psf/trademarks/) отдельно допускает derived logos для свободно распространяемых сторонних модулей и инструментов, относящихся к Python. Для коммерческого использования модифицированного знака действуют дополнительные условия. Назначение карточки соответствует обозначению языка; будущие коммерческие варианты и материалы должны быть проверены отдельно. Заявление в README, что знаки не означают аффилиацию, полезно, но не заменяет лицензионные права.

### 11. Модули распространяются отдельно без собственного лицензионного комплекта

Каждая из 11 записей текущего реестра перечисляет только `module.json` и `cover.png`. В manifest нет `license`/`author`; в каталоге скачиваемого модуля нет notices. Правовые материалы из корня Git-репозитория при такой установке не передаются.

Для собственной оригинальной грамматики/шаблона отсутствие поля лицензии само по себе не доказывает нарушение автором своих прав. Но получателю неясны условия повторного использования, а обязательные сведения для чужой графики должны сопровождать и отдельно получаемый модуль. Необходимо добавить лицензионные материалы в файлы модуля и индекс реестра; одновременно уточнить условия использования генерируемых шаблонов.

## Приоритетный порядок исправления

1. Исправить сборку notices: полные лицензии и copyright Rust-компонентов, Lucide/Feather и реально встроенных fallback-шрифтов.
2. Доукомплектовать SBCL по точной версии и всем включённым contrib, не ограничиваясь главным COPYING.
3. Добавить атрибуцию HTML5; разобраться с условиями Bash либо заменить этот знак; проверить способ использования C++.
4. Передавать обязательные уведомления вместе с отдельно скачиваемыми модулями и их обложками.
5. Добавить лицензионные материалы Zstandard и остальных нативных компонентов; закрыть схему предоставления исходников Portable Git и проверить применимость MPL.
6. Пересобрать и повторно проверить каждый конечный архив/установщик. Изменение только репозитория не исправляет уже скачиваемый rc6.

Его успешный запуск в будущем будет полезен для политики зависимостей, но не заменит проверку конечной упаковки, ресурсов, атрибуций и доступности исходников.
